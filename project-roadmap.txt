NAVIGATION & TRACING PATH
- path actions bar before start: Undo, Redo, Cancel, Start + snap toggle (Free/Foot/Bike/Car, Force)
- while running only the data pill is shown (distance, duration, ETA for navigation),
  on start/resume show toast msg where to click to pause
- while running (Android) a live notification shows the time passed hh:mm and the distance passed
  along the route, titled "Navigating" / "Tracing path", "Navigation paused" / "Tracing paused" when paused;
  it is removed on cancel or completion; it is separate from the path recording notification,
  so recording and navigating/tracing at the same time show two notifications, each with its own time and distance
  - when nothing is recording, the navigation/tracing notification IS the location service's own
    (taken over in place), so a trace on its own shows one notification, not two; ownership moves
    to the recording when one starts and back again when it stops, so the service is never left
    without a notification
- while running (Android) navigation/tracing holds a share of the same background location watcher
  the path recording uses, so the route keeps being followed with the screen off and the app off
  screen. There is only ever ONE watcher, reference counted between the recording and the route:
  the plugin's service keeps a single foreground notification and re-foregrounds on every watcher
  added, so a second watcher would overwrite the first's notification
  - the watcher is a failover for the route, not its source: the WebView's 500 ms geolocation poll
    is twice the watcher's 1 Hz and keeps the camera smooth, so the watcher only feeds the route
    once that poll has gone quiet, which is what a hidden WebView does to its timers
  - watcher fixes are fed into the same "geolocate" event the poll fires, so camera, road
    snapping, passed path, off-path detection and the trace completion test all stay in one place
  - the watcher runs at a 2 m distance filter for the trace's benefit; the recorded line's old 5 m
    thinning is applied in JS instead, so recorded geometry is unchanged
- start/resume starts user tracking bearing, stop/cancel stops it
- location control icons: track location - ion-icon name="locate-outline",
  start user tracking bearing - ion-icon name="navigate-outline",
  stop user tracking bearing (= pause) - ion-icon name="pause-outline"
- clicking stop user tracking bearing pauses navigation/tracing:
  it keeps the traced progress and the traced overlay on the map, brings back the actions bar
  with the route editable again and Start renamed to Resume
- clicking start user tracking bearing starts, or resumes, navigation/tracing if a route is laid out
  (same as Start/Resume in the actions bar), otherwise it only moves the camera
- tracing path
    - on start tracing the path is snapped if it is a snapped path, otherwise it is traced free
    - to start tracing the user must be within 10 m of the path start point,
      to resume within 10 m of the last traced point, otherwise show toast msg
    - when the user leaves the path the traced progress stays at the point where he left it,
      it continues only when he returns within 10 m of that point,
      returning anywhere else does not trace the skipped part
    - the tracing is completed only when the user is near the end point (10 m)
      and the whole path is passed (unwalked path length is 0):
      show toast msg "Tracing completed.", the path returns to its normal look
      and user tracking bearing is stopped
    - a completed tracing is recorded on the path (date, start time, finish time, duration);
      the duration counts only the time spent tracing, paused time is not part of it
    - a cancelled tracing records nothing
    - a finished path recording leaves the same kind of record on the path it creates,
      for the walk that recorded it; paused time is not part of its duration either

- embedded code - const iframe = `<iframe style="width: 100%; height: 100%; border: none;" allow="fullscreen" scrolling="no" src="<link>"></iframe>`;
    - the copied link always carries &embedded=true&style=<idMapStyle>
- embedded options (opt-in, hand-added to the copied link; only meaningful with &embedded=true)
    &interact=true                              pan/zoom immediately (no activating tap/click first),
                                                alias cursor on hover over markers and finished paths
    &geolocation=true                           show and enable the location control (locate + bearing)
    - NOTE: &geolocation=true also needs the host iframe to delegate the permission, otherwise
      Permissions-Policy blocks navigator.geolocation on any cross-origin site. Edit the snippet to:
      <iframe ... allow="fullscreen; geolocation" ...></iframe>
    - the "Open in RontoMap" logo strips embedded, style, interact and geolocation from the link
- embedded events - posted to the embedding page with window.parent.postMessage({source:"rontomap", type, ...}, "*")
    ready           { styleId }                 the frame takes commands; sent once per frame load, and
                                                with &features_collection only once they are on the map;
                                                styleId is the basemap it opened with
    style-change    { styleId }                 the basemap changed, from the style control or set-style;
                                                only after ready, which already carries the opening style
    marker-click    { marker: {name, description, lng, lat, isSight, index} }
    path-click      { path: {name, description, isCircuit, roadSnap, distance, duration, index, lng, lat} }
- embedded commands - posted by the embedding page with frame.contentWindow.postMessage({source:"rontomap-embed", type, ...}, origin)
    - only in embedded mode, and only from the window that embedded the frame
    - wait for the ready event: commands sent before it are dropped
    set-features    { collectionId }
                    swaps the whole features collection in place, no frame reload — so the
                    camera, the chosen style and everything else on screen survive it
    show-marker     { sightId, zoom, duration }
                    flies to the marker whose description carries that id as JSON
                    ({"id": ...}); does nothing at all if no marker has it
    set-camera      { camera: {lat, long, zoom, bearing, pitch, duration} }
                    flies the map there without reloading the frame; lat/long required,
                    zoom defaults as ?lat/?long does, bearing/pitch/duration keep current/1000ms
    set-style       { styleId }
                    swaps the basemap in place, no frame reload; one of rontomap_streets_light,
                    rontomap_streets_dark, rontomap_satellite. Not saved to localStorage the way
                    the style control is: it follows the embedding page, and must not overwrite
                    the style chosen for rontomap on its own. Ignored if already that style.
